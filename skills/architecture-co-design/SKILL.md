# 架构共创

## 核心目标

调查实际代码与使用场景，结合用户经验和偏好，用具体样本明确**模块归属、阅读路径、修改范围及其取舍**。
只对影响方案的未知提问，用阅读与变更推演检验设计，并区分已确认决策与建议。

## 协作边界

- 先使用当前对话、项目约定和相关代码，不重复询问已知信息。默认偏好不是项目事实。
- 从使用场景、下游用途与失败后果明确核心需求，区分目标、约束和实现办法；保留现有合理设计，将新增能力融入其职责与契约，依据具体问题决定替换范围。
- 区分已确认要求、已观察事实、建议、暂定假设和待决问题。只有用户明确接受的决策称为共识；授权内可自主推进的选择标为“授权内自主决定”。
- 讨论方案不等于授权修改代码。已获实施授权时，不重复索取同一授权；遇到超出范围的改动、关键边界变化或高影响未知，再说明并协商。
- 不为套用本 Skill 而迁移现有项目，不擅自改变技术栈，不把一个项目的业务约定传播到其他项目。
- 新建或更新设计文档需遵循用户授权和项目惯例。默认先在对话中收敛；优先更新已有文档，不建立多个相互矛盾的事实来源。
- 不把可读性优化当作删减业务校验、权限控制、安全保护、失败处理或兼容行为的理由。

## 按需加载参考

- 用户反馈模糊、双方发生分歧，或需要示范有效提问时，读取 [对话示例](references/dialogue-examples.md) 的相关部分。
- 需要交付或持久化正式方案时，读取 [设计共识模板](references/design-agreement.md)。按规模裁剪，不为填满模板制造内容。
- 简单问题不必加载参考文件，也不必展示以下完整流程。

## 协作流程

按任务规模选择以下步骤。信息充分时直接推进；出现实质分歧时，只处理受影响的决策。

### 1. 建立共同理解

从上下文和代码中明确以下内容，缺少影响决策的信息时再提问：

- 本次要解决什么实际问题，什么不在范围内。
- 用户阅读或修改代码时，具体在哪里遇到阻力。
- 哪些行为、兼容性、团队约定和外部接口必须保留。
- 最可能发生什么变化，哪些扩展明确暂不需要。
- 关键副作用与观测需求是什么，哪些事实需要记录，记录失败是否影响业务。

有仓库时，按问题范围阅读项目说明、相关目录和一个代表性功能的真实调用链；不要只凭目录名评价架构，也不要先扫描全仓库。未读取的内容不能当作事实，无仓库时明确样本是假设设计。

用简短复述暴露理解偏差，例如：“这次主要解决修改报表规则要跨多个技术目录的问题，不更换数据库，也不重做所有功能。”若上下文已明确，不重复铺垫。

### 2. 找出真正影响决策的未知

每轮默认只问 1～3 个有决定作用的问题；没有关键未知就不问。

每个问题尽量包含：**为什么问、答案影响什么、信息不足时推荐怎样暂定**。让用户回答业务情境，不要求先选择 DDD、分层架构等术语。

- 能从代码验证的事实，先自行验证。
- 低风险、可逆细节可标注假设后继续。
- 影响数据安全、外部契约、模块职责或迁移范围的未知，先澄清或提出最小验证方法。
- 用户不确定时，提供具体情境或局部对比帮助判断；不要反复追问同一问题。
- 用户要求自行判断时，在授权范围内采用保守且可逆的默认值，列出重要假设，不无限等待确认。

### 3. 提出最小设计样本

先给推荐结论、依据和适用边界，再展示样本；存在实质取舍时才比较备选。已获实施授权且信息充分时，直接落实推荐。

选择一个真实功能，按需展示：

1. **浅层目录树**：谁拥有该功能，哪些组成自然集合；让管理机制与具体成员容易分别定位。
2. **代表性行为链路**：说明依赖组装，沿入口和子流程检查到具体操作；各层组织业务阶段时优先函数组合，局部算法直接实现。按共同意图分组留白，展示关键数据、副作用和失败边界。
3. **模块边界**：负责什么、不负责什么；区分包含关系、执行关系与使用依赖。
4. **修改推演**：改变一个成员或一条共同规则，分别落在哪里，为什么不会无谓扩散。

日志参与职责与执行边界的设计：业务拥有事件含义，应用或运行时统一配置输出能力，
执行边界负责耗时与状态观测，请求关联字段通过作用域传播并隔离并发执行。
一般诊断输出、必须持久化的操作记录、随计算返回的解释分别确定失败和交付语义。
复用已有日志或效果系统，统一入口不要求逐层注入 logger；可复用库或多实例的不同实现需求可显式注入。
涉及具体流程与日志表达时结合 `structure-expression`，复用同一份调查与样本。

已有项目优先展示必要的局部调整，与现有合理设计融合，不绘制无关目录。不要预建空层级、空接口或尚无用途的框架。

邀请用户评价具体位置，例如：“规则放在报表模块内部，你修改时是否能直接定位？”而不是只问“这个方案满意吗”。不必让用户逐项批准命名等可逆细节。

### 4. 根据反馈修正理解

面对“太绕”“太碎”“不好扩展”等反馈，先定位问题类型，不立即决定拆分或合并：

| 问题 | 应检查的内容 |
|---|---|
| 归属不对 | 是否放错父级、由错误的模块拥有规则或状态 |
| 包含关系不对 | 是否把调用、依赖、同页面或相同生命周期误当作组成关系 |
| 同级组织不清 | 是否将管理机制与大量具体成员混排，缺少有语义的集合边界 |
| 粒度不对 | 是否拆散同一语义，或把无关职责聚在一起 |
| 阅读路径不对 | 是否能分别找到整体组装与成员行为，每次深入是否获得有意义的信息 |

结合此前已确认要求还原完整目标，用实际代码定位阻力，再展示对应的目录或调用对比。
问题可能同时存在：归属错误调整所有权，集合混排调整分组，同一行为被拆散或职责重复时考虑合并。
子模块不必成为独立领域，集合分组也不要求新增执行框架。

只修正受影响的决策，说明收益、代价和修改范围；已有实施授权时完成对应纠正。
用代码、运行表现与用户反馈检验结果，并将修正后的理解用于后续工作。
用户偏好与正确性或项目约束冲突时，指出具体冲突并给替代方案。
临时取舍和未确认推断不作为长期偏好。

### 5. 用阅读与变化验证

检查主要在内部完成，只向用户呈现发现的问题和需要权衡的决策。

**阅读推演**

- 涉及成员集合时，能否分别找到父级组装、共同机制和具体成员，而不是在混排文件中猜测入口？
- 进入一个成员能否直接读到完整行为，还是需要拼接定义、动作表与多层回调？
- 当前阅读单元是否处于相近的抽象层次，入口与子流程是否都展开了实际关系，语义分组和每次深入是否帮助理解？
- 名称和契约能否传达主要副作用及失败语义，是否把使用依赖误画成包含？
- 日志能否关联本次执行、定位关键业务事实，并区分尝试失败与最终结果；观测是否挤占流程或造成多层重复组装？

**变更推演**

- 选 1～3 个高概率变化，区分修改成员与修改共同规则，列出实际影响范围。
- 检查规则是否有明确所有者，管理机制是否不必要地硬编码成员差异。
- 必要时推演删除一个功能：是否能清理其实现、测试、配置和调用，又不误删共享能力。
- 对新增模块、集合目录或抽象说明语义与阅读收益；不是仅搬文件，也不为分组增加无用框架。

推演是设计证据，不等于编译、测试或运行验证。明确区分已验证与待验证内容。

### 6. 收敛并衔接实现

满足以下条件即可收敛，不追求预知所有未来变化：

- 目标、非目标和主要约束明确。
- 关键责任边界没有未处理的实质分歧。
- 至少一个代表性功能的阅读与修改路径能说清楚。
- 剩余假设已标记，不阻塞安全的下一步。

根据用户请求输出简短结论或正式方案。未确认部分标为建议或待决，不能把整份草案称为已确认。

仅授权设计时，在方案与下一步建议处停止。已授权实施时，优先落地一条有代表性的完整链路，再进行必要的构建、测试和边界检查；不要先建立大量空壳。只有在这些验证完成后才报告通过，无法执行时说明原因。

旧项目实施前明确迁移、兼容和清理范围。不默认保留转发层，也不默认删除旧入口；根据调用方和外部契约决定。
被替代实现的相关调用、配置、依赖与说明同步清理；验证聚焦真实行为、稳定契约和重要风险，
复用充分证据，同步精简重复或失效测试，保留必要的业务、权限与数据完整性保障。
实施中若假设失效，回到受影响的决策，不静默扩大重构。

## 默认设计取向

在没有相反项目约束时，以这些偏好作为起点，而不是不可修改的教条：

- **包含与归属清楚**：父级定义领域或子系统，子级表达自然组成；完整成员可以独立成模块，不以独立领域地位或代码量为门槛。
- **同级组织有语义**：管理机制与具体成员集合应容易区分，按集合含义分组而非机械按文件类型分类；不为对称预建层级。
- **渐进披露**：目录用于定位组成与成员，组装入口连接能力，成员入口表达完整行为，深入后才展开细节；不为每级目录增加转发函数。
- **依赖与执行可追踪**：调用顺序不等于包含关系。机制通过共同契约使用成员，由组装入口绑定具体实现；成员协调外部能力，不接管其领域规则。跨模块使用明确入口，避免循环依赖和深入导入内部实现。
- **抽象按实际价值判断**：抽象用于表达清晰的领域概念、封装完整行为或集中共同规则。结合阅读收益、修改影响与维护成本判断其价值；复用不是建立抽象的唯一理由。
- **为真实变化留空间**：优先考虑已知的扩展方向，不为所有假想变化搭建插件系统。
- **共享需有理由**：代码相似不等于同一职责；共同的业务规则应有明确归属。不要让 shared、common、utils 成为归属不明代码的收容所。
- **简洁不隐藏风险**：事务边界、重要副作用、失败处理和安全约束不能被漂亮函数名掩盖。

不使用机械的目录深度、文件数或函数行数作为质量判据。偏离默认取向时，用实际收益和代价解释，不以设计模式名称代替论证。
