# 评审报告与判断示例

按评审规模裁剪，不为填满标题生成发现。以下样例均为假设，不是实际项目结论。

## 1. 报告骨架

```markdown
# 架构评估：<对象>

## 结论与范围
- 结论：<保留为主 / 局部调整 / 存在需处理的边界问题>
- 基准：<本次要求、项目决策、适用偏好及例外>
- 已读链路：<组装 → 主流程 → 子行为 → 具体操作>
- 未覆盖：<其他入口、运行时配置、外部系统等>

## 值得保留
- <具体设计、位置与收益>

## 主要发现
### <标题>
- 类型 / 行动：<实际风险、偏好偏离或可选改善> / <优先级与理由>
- 证据：<实际文件:行号或符号，相关调用方与契约>
- 基准：<适用原则及来源>
- 判断：<已观察事实 → 后果或变化场景>
- 最小建议：<改变什么、保留什么>
- 代价：<调用方、迁移、测试或复杂度成本>
- 置信度：<高 / 中，依据或尚存限制>

## 变化推演
| 场景与依据 | 必要修改位置 | 无关牵连与原因 | 判断 |
| --- | --- | --- | --- |

## 待核实与验证
- 待核实：<疑点、缺少的证据、最小确认方法>
- 已执行：<源码阅读 / 推演 / 实际检查命令及结果>
- 未执行：<测试、运行或故障复现等>

## 下一步
<建议先处理的事项、可延后项；无调整必要时明确保留。>
```

位置应来自实际读取的文件；用符号定位时写出文件及符号名。没有代码时改用设计章节或片段位置，不能编造行号。
优先级不是自动阻断规则。只有已知交付标准或有证据的高影响风险才能支持“交付前必须处理”。

## 2. 必要注册与无谓传播

**样例 A：合理设计。** 新增 `builtins/export/` 时，需要在 `commands/index.ts` 注册成员并补成员测试。
`dispatch` 仅调用共同的 `execute` 契约。这是必要组装变化，不应要求新增功能永远不修改现有文件。
允许显式注册；没有动态发现需求时，不建议为“零修改”引入插件框架。

**样例 B：需要调查。** 新增成员还要在调度、权限和 UI 三处增加同名分支。
先确认这是否是三个不同规则的合理归属，还是同一事实的重复维护。
若成员的相同权限声明被复制到多个位置，且实际调用链显示遗漏一处会漏校验，才可报告具体权限风险。
若只有同步维护成本证据，报告维护风险，不宣称已能绕过权限。

示例发现：

> **实际风险（维护） / 后续处理**：同一成员能力声明在注册、过滤和帮助生成处重复维护。
> 三处逻辑均以同一能力字段决定是否暴露操作；新增成员必须同步更新，否则列表与实际可执行集合不一致。
> 建议让声明由成员提供、各机制消费同一契约，而不是集中所有业务规则。
> 代价是调整契约及三个消费者，并验证现有成员行为。此处为推演，尚未执行新增成员实验。

## 3. 并发状态：同一外观，不同结论

分支在 `Promise.all` 内分别写 `ctx.evidence` 和 `ctx.metrics`：

- 如果一次运行创建一个 Context，失败后整个 Context 被丢弃且没有其他观察者，可能构成适用偏好的偏离，
  但不能仅凭并发写不同字段宣称存在跨请求污染或同字段竞争。
- 如果一个分支成功写入，另一个失败，而 catch 在同一 Context 上重试并读取残留值，
  应沿状态创建、写入、catch 与重试消费者说明故障路径，再报告实际风险。
- 分支返回独立结果，全成功后汇合赋值，可以避免本组字段的部分提交；
  它不自动取消仍运行的分支，也不回滚已经发生的网络、数据库或其他外部副作用。

判断来源是具体执行语义，不是“共享”“可变”或“并行”这些词本身。

## 4. 保留真实边界，不机械深模块化

`research` 只有一个调用方，但封装完整检索与合并行为；另一个很短的包装负责权限校验、事务和资源释放。
二者都不能因为单次使用、短小或增加一次跳转而直接删除。

对纯转发层，应检查兼容入口、协议转换、生命周期或公开 API 稳定性是否赋予它真实价值。
若没有这些作用且确实增加阅读负担，可列可选改善；若阅读负担也不明显，不必报告。
不能以“深模块”为由合并不同规则所有者，也不能为了满足长度阈值拆散完整行为。

## 5. 偏好与项目取舍

项目明确决定在生成代码中保持直接导入，用户默认偏好在组装入口注入。
先检查该规则是否真的适用于当前文件，以及生成链路是否允许手工改变。
如果属于明确的项目例外，保留它并说明适用范围，不在每次评审重复报同一条偏好违规。
若该决策带来有证据的正确性风险，仍需报告风险及重开决策的理由，不能被“已确认”遮蔽。

## 6. 证据不足时的有效结论

仅有目录树和两行调用变更，不能判定 `shared/` 归属错误，也不能从“修改了四个文件”推出过度耦合。
可先指出需要验证的假设，再请求最小材料，例如该入口的完整调用链、规则与状态所有者、涉及的组装和契约。
此时输出“尚不能判断实现边界”，而不是“通过”或“发现四处架构缺陷”。
