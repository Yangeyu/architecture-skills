# 架构评估

## 目标与职责

回答：**当前设计哪些值得保留，哪些不符合适用的设计原则，哪些变化会暴露边界问题，是否值得现在调整。**
评估必要协作是否通过清晰契约发生，以及变化是否无谓扩散；不是追求零依赖、最多接口或最少文件。

本 Skill 负责调查、验证与形成结论，不另建一份个人设计原则：

- `structure-expression` 提供结构与表达偏好；评估个人偏好匹配时加载它，并仅按涉及的问题读取其参考。
- `architecture-co-design` 提供架构取向和已确认方案的协作边界；涉及职责与边界判断时加载相关内容作为依据，不重跑共创问卷。
- 使用当前项目的约定、ADR、用户已确认决策及相关记忆补足上下文。记忆中的代码事实需重新核对。
- 配套 Skill 不可用时，使用用户明确给出的原则与项目约定；明确缺少哪些依据，不声称已经检查未知的个人偏好，也不为评审自动安装依赖。

## 评审边界

- 默认只读：不改源码、测试、配置或设计文档，不自动创建报告、安装工具或启动有外部副作用的程序。
  用户要求保存报告时才写入指定或项目惯用位置。测试可能写入数据库、生成文件或调用网络，运行前检查其影响与授权。
- 已有明确的修复授权时，先完成对应判断，再衔接实施；不要重复索取同一授权，也不把评审请求解释为全仓重构授权。
- 当前明确需求、项目硬约束与已确认决策用于确定本次基准；个人默认偏好不能静默覆盖它们。
  若彼此冲突或存在安全、正确性风险，说明冲突和后果，不为了服从偏好而隐藏风险；只对影响结论的未知提问。
- 分清已观察事实、推演、假设与未验证项。目录名称、函数名称、类型外观和注释都不是行为已经成立的证据。
- 不以代码行数、文件数量、复用次数、设计模式名称或统一的打分替代判断。
  不设问题数量指标，不把“暂未发现问题”包装为整个系统已通过认证。
- 本评审不是完整安全审计或性能基准测试。发现相关风险应报告，未覆盖的专项检查应注明。

## 执行流程

多步骤评审用 TODO 跟踪范围、调查、推演和交付；轻量局部评审可合并步骤。复用已有调查，不为填表扩大范围。

### 1. 明确范围与基准

先从请求和现有材料确认，不重复询问已知信息：

- 对象：模块、子系统、设计稿，还是一段 Git 变更。明确入口、目标和非目标。
- 基准：本次用户要求、项目约定/ADR、适用偏好；记录来源及例外，只提取本次有关的规则。
- 场景：真实使用方式、需要保留的契约，以及最可能出现的变化。

未指定范围时，先看项目说明和浅层结构，再按用户痛点或近期变更热点选择代表性链路；不要默认读完整个仓库。
变更评审先确认实际 diff 范围，再向外读必要的调用方、契约和测试，区分新增问题与原有问题。
没有 Git 变更不妨碍现状评估。范围无法确定且会显著影响成本时，问一个具体的范围问题。
只有设计稿或片段时可评估其自身关系，但不能给未提供的实现编造文件位置或结论。

### 2. 沿实际链路建立结构理解

从一个代表性用例的组装入口开始，沿业务流程、子流程读到具体操作。不要只看顶层或止于漂亮的函数名。
按需核对调用方、公开契约、内部导入、状态创建与写入、失败处理和相关测试。

将以下关系分开理解，必要时用小表或简图记录，不强制绘制全仓图：

| 关系 | 要查明的事实 |
| --- | --- |
| 归属与组成 | 谁拥有规则、数据和状态；目录是否揭示实际组成 |
| 协作与依赖 | 谁调用谁、谁选择实现、通过什么契约，是否越过边界访问内部细节 |
| 执行与生命周期 | 阶段、分支、并发、资源与状态怎样流转；副作用和失败由谁负责 |

检查方向不是新的偏好标准；具体判据取自第 1 步的基准：

- **边界与内聚**：完整行为是否集中，规则是否有明确所有者；共同机制是否硬编码具体成员差异。
- **依赖与隔离**：必要协作是否显式，公开接口是否泄漏内部模型；循环、共享可变状态或时序约定是否造成额外牵连。
- **粒度与阅读**：每次深入是否获得有意义的信息；短模块是否承担真实契约，长模块是否混入无关职责。
- **表达与数据**：各层流程能否追踪；参数、Context、执行策略与视觉分组是否符合适用偏好，是否存在合理例外。
- **副作用与失败**：事务、资源、日志、取消、重试和并发边界是否明确；实现与声明的契约是否一致。

依赖扫描只能发现结构线索。没有循环依赖不等于没有耦合；多个模块共同依赖一个类型也不自动意味着设计错误。
优先复用现有工具，不为了这一步引入依赖分析平台。

### 3. 用变化检验隔离程度

从已有需求、历史变化或用户痛点选择 1～3 个高概率变化；没有依据时明确标为假设，不凭假想未来要求扩展框架。
可选：新增一个成员、修改局部规则、修改共同规则、替换外部适配或删除一个功能。

每个推演记录：

1. 变化的具体内容和依据。
2. 预计修改的实现、组装、调用方、测试与配置；与当前代码关系核对。
3. 哪些传播是契约变化、注册或验证所必需，哪些只是内部细节泄漏导致的无关同步修改。
4. 现有边界如何承接变化，或调整哪里才能缩小不必要的影响；同时说明代价。

新增成员需要修改组装入口、契约升级需要调整调用方，都可能完全合理。
跨文件数量只是线索；只有解释清楚传播原因，才能把它作为耦合问题。
推演不是已实施的实验，也不是编译、测试或运行验证。

### 4. 反证与分类

形成发现前主动尝试推翻它：

- 是否存在没读到的调用方、运行时配置、代码生成规则或项目约定，可以解释当前设计？
- 去掉这层抽象，复杂度是真的减少，还是仅移到调用方，并丢失权限、事务、协议或生命周期边界？
- 建议是否只是形式更符合偏好，却增加跳转、参数搬运、同步配置或维护成本？
- 是否把必要注册、真实业务差异或已批准的阶段性取舍误判为耦合？

证据不足时补读最相关位置，或将其降为待核实项，不能写成确定缺陷。

| 类型 | 使用条件 | 报告方式 |
| --- | --- | --- |
| 实际风险 | 有行为失败条件，或可说明的维护后果，如规则重复导致修改必须同步 | 写清触发场景、影响与证据；维护风险不冒充已发生的运行错误 |
| 偏好偏离 | 与本次适用且已知的个人/项目原则不符，但未证明实际损害 | 引用原则，解释偏离与例外；不自动阻断交付 |
| 可选改善 | 当前设计合理，仍存在有具体收益的替代方案 | 说明收益、成本和为何可延后；没有具体收益则不列 |

同一根因合并为一个发现，类型可附带说明，不重复计数。
问题性质、行动优先级和证据置信度分开：重要不等于确定，偏好偏离也可能是本次明确验收项。
按影响、变化频率、触发概率与修复成本给出“本次应处理 / 后续处理 / 可不改”，避免无依据的严重等级。
置信度用“高 / 中 / 待核实”并说明依据；待核实项单列，不列为确定发现。

### 5. 交付与衔接

结论先行，默认不报总分，不复述完整清单。每个确定发现至少包含：

**类型与优先级 → 文件/符号及可核对的位置 → 适用原则 → 事实与关系 → 后果或变化场景 → 最小建议及代价 → 置信度。**

报告包含：

- **结论与覆盖范围**：对象、实际读取的代表性链路、使用的基准与未覆盖范围。
- **值得保留的设计**：有证据的有效边界或表达，不为了平衡措辞硬凑优点。
- **主要发现**：先高影响且证据充分的项，合并同根因问题。必要时附关键代码或关系图。
- **变化推演**：简述场景、预期改动范围、必要与不必要的传播。
- **未知与验证状态**：区分源码阅读、推演、实际执行的检查及结果；列出改变结论所需的证据。
- **下一步**：优先保留什么、先调整什么、哪些不值得当前重构。

无确定问题时直接说明在本次范围内未发现需要调整的问题，并保留覆盖边界，不强行生成建议。
局部问题可用几段话交付；需要完整报告或分类样例时读取 [评审报告与判断示例](references/review-report.md)。
仅报告最小调整方向，不默认设计整套替代架构。需要协商职责或重要取舍时衔接 `architecture-co-design`；
已授权实现时由 `structure-expression` 指导落地，复用本次证据、适用基准与推演，不重新开始调查。

## 交付前检查

- [ ] 范围与基准有来源，配套原则不可用或存在冲突时已说明。
- [ ] 判断基于实际读取的链路；仅有设计材料时没有冒充实现结论。
- [ ] 发现有位置、关系、后果或偏好依据；已考虑合理例外和反证。
- [ ] 必要协作与无谓耦合已区分，没有机械套用层数、长度、接口或复用次数规则。
- [ ] 变化推演对应具体影响位置，未把推演当作运行验证。
- [ ] 实际风险、偏好偏离、可选改善与待核实项未混淆；建议成本与保留项明确。
- [ ] 未越权修改或执行有副作用的操作，TODO 与实际验证状态一致。
