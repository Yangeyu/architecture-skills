# Structure Expression

## 1. 目标与结构模型

将用户的阅读偏好落实为正确、可维护、易理解的高质量代码，而不只是给出整齐的目录或简短入口。
让读者沿结构理解系统：**找到归属 → 看清组成 → 阅读行为 → 按需展开细节**。
主动选择有表达收益的结构与抽象；简洁是减少理解负担，不是减少文件、层数或代码行数。
用实际阅读与变更场景验证表达，不以形式统一或篇幅更短代替质量判断。

| 关系 | 表达职责 |
| --- | --- |
| 包含与归属 | 目录与模块说明“属于谁、由什么组成、规则和状态由谁拥有” |
| 执行 | 函数、组合与状态转移说明“如何执行、数据与副作用如何传递” |
| 使用与依赖 | 显式注入与组装说明“需要谁的能力、由谁选择具体实现” |

目录树不必复刻调用图。同页面、先后调用或同生命周期不能单独证明包含关系；
协调外部能力不改变其规则与状态的所有权。

## 2. 默认设计偏好

### 目录：先语义维度，再信息密度

- 层级应揭示父模块的组成，并形成集中阅读和扩展的位置；子模块不必自身成为独立领域。
- 稳定的组织机制与可增长的成员集合分开表达，例如 `commands/builtins/`。
  已有明确集合身份和增长方向时，不等文件多了才分组。
- 进一步的内部细分按阅读压力决定。小规模 `research/` 可以平铺，来源增多时再分出 `sources/`；
  文件数量是线索，不是阈值，也不为假想扩展预建空层级。
- 函数命名行为，文件承载独立模块，目录组织实际组成，三者分别判断。
  完整成员即使短也可独立；短小、局部使用且无独立扩展预期的步骤通常留在同文件。
  `copy.ts` 与 `export/` 可以并列，语义一致不要求外形一致。

### 协作：依赖显式，行为完整

- 外部业务能力默认通过参数或创建函数注入，由组装入口选择实现；即使只有一个实现，
  也提供阅读价值，不仅用于测试或替换。类型、常量及模块内部实现可正常导入。
- 有成员集合时，机制承载共同规则，成员集中定义与完整行为，组装连接两者。
  普通依赖对象或函数契约即可，不把所有模块套成管理机制、接口文件和工厂层。

### 流程：整体看阶段，局部看关系

- 有明确业务阶段时，**优先函数组合**，适用于入口与各级子流程。
  参数不同或存在跨阶段依赖时，用简短匿名函数、闭包或明确数据形状就地衔接，
  不因此自动退回整段显式调用，也不强制统一 Context。
- 影响当前流程路径或结果的策略在组合处显式表达，例如 `withFallback(research, readCachedEvidence)`；
  阶段本体保持简洁，策略实现继续下沉。
- 有完整业务含义的行为可命名为子流程，深入后仍能读清阶段；命名不自动要求独立文件。
  已有显式调用清楚时可保留，局部资源或异常处理也可直接表达。
- **控制流保持浅层**：避免多层 `if / for` 交织和复杂组合括号树。
  用卫语句、提前返回或 `continue` 排除例外，把完整子行为下沉；
  不靠碎片函数隐藏嵌套，也不把业务层级或调用链限制成固定层数。
- 阶段关系为主时用 Flow，节点转移与回环为主时用 Graph 或已有状态机，两者可分层配合。
  Fluent 按语义是否局部、连续来选择，而非为了链式外观。

### 视觉：让排版参与表达

用空行分组阶段、节点与异常处理段，相关语句就近组织；链式关系和复杂参数按阅读需要分行。
注释补充意图、取舍与关键约束，而非逐行翻译代码。遵循项目格式约定，
但不为缩短样例压成密集单行，也不以排版代替职责整理。

## 4. 应用与验证

### TODO 跟踪

多步骤任务开始前建立 TODO，按实际工作列出调查、设计、实施、清理与验证等具体任务，
执行中及时更新待办、进行中与已完成状态。有任务工具时使用工具，否则维护 Markdown 勾选清单。
完成一项更新一项；验证未执行或存在阻塞时明确标出，不以“代码已写完”代替“验证已通过”。
简单单步任务可省略，不为填满清单扩大范围。

### 执行流程

按任务规模执行，不重复启动完整架构讨论：

1. **查明阻力。** 读项目约定、相关目录与代表性调用链，区分归属、维度、密度、粒度和执行表达问题；
   无代码时标明样本是假设，不因“太碎”直接合并，也不因“要扩展”直接搭框架。
2. **展示完整阅读路径。** 给出必要的目录与流程，沿一条链路展开子流程及关键实现。
   检查每次深入是否获得实质信息，数据关系、策略、依赖与控制边界是否可追踪。
3. **推演高概率变化。** 新增成员、修改局部规则或共同规则应有自然位置；
   说明新增抽象的阅读收益与代价，不推演所有未来可能。
4. **按授权落地。** 纯定位问题可只整理目录；职责分散才需要同步收拢职责。
   明确调用方、契约、测试和文档范围，清理被替代的内部路径，保留或迁移必要公开入口。
   重大归属取舍结合 `architecture-co-design`，复用已有共识；讨论不等于实施授权。

结构调整保留输入输出、权限与业务校验、数据依赖、副作用顺序、事务与资源所有权，
以及异常、超时、取消、重试、补偿、并发、幂等和生命周期语义。
顺序改并行、新增回退等是行为变化，需明确授权并验证；共同契约不能抹平成员真实差异。
权限、事务、协议适配等真实边界不能因代码短或只有一个实现而删除。

优先复用现有能力，允许支撑选定表达的最小工具；工具须保留真实类型与执行契约。
调度、持久化和恢复由实际运行需求决定，不由组合或 Graph 样例推导出来。

交付结构判断、必要样本、收益与代价、实际修改范围及待验证项。
区分阅读/变化推演与编译、测试、运行结果，不把文档检查当作行为验证。
