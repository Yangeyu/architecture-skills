# Structure Expression

## 1. 目标与结构模型

组织目录与代码，让读者沿**找到归属 → 看清组成 → 阅读行为 → 按需展开细节**理解系统。
用实际阅读路径和修改范围判断结构价值，不以文件数、层数、行数或形式统一判断质量。
新建功能从完整使用场景形成结构；改进现有设计时先核对职责与契约，
将新增能力融入合理的组织方式，只对有实际问题的部分删除、合并或重建。

| 关系 | 表达职责 |
| --- | --- |
| 包含与归属 | 目录与模块说明“属于谁、由什么组成、规则和状态由谁拥有” |
| 执行 | 函数、组合与状态转移说明“如何执行、数据与副作用如何传递” |
| 使用与依赖 | 显式注入与组装说明“需要谁的能力、由谁选择具体实现” |

目录树不必复刻调用图。同页面、先后调用或同生命周期不能单独证明包含关系；
协调外部能力不改变其规则与状态的所有权。

## 2. 默认设计偏好

### 目录：先语义维度，再信息密度

- 层级应揭示父模块的组成，并形成集中阅读和扩展的位置；子模块不必自身成为独立领域。
- 稳定的组织机制与可增长的成员集合分开表达，例如 `commands/builtins/`。
  已有明确集合身份和增长方向时，不等文件多了才分组。
- 进一步的内部细分按阅读压力决定。小规模 `research/` 可以平铺，来源增多时再分出 `sources/`；
  文件数量是线索，不是阈值，也不为假想扩展预建空层级。
- 函数命名行为，文件承载独立模块，目录组织实际组成，三者分别判断。
  完整成员即使短也可独立；短小、局部使用且无独立扩展预期的步骤通常留在同文件。
  `copy.ts` 与 `export/` 可以并列，语义一致不要求外形一致。

### 协作：依赖显式，行为完整

- 外部业务能力默认通过参数或创建函数注入，由组装入口选择实现；即使只有一个实现，
  也提供阅读价值，不仅用于测试或替换。类型、常量及模块内部实现可正常导入。
- 有成员集合时，机制承载共同规则，成员集中定义与完整行为，组装连接两者。
  普通依赖对象或函数契约即可，不把所有模块套成管理机制、接口文件和工厂层。
- 日志等横切能力优先复用应用或运行时统一入口，在应用边界配置后端、格式与级别；
  requestId、runId 等字段通过执行作用域关联并保持并发隔离，不作为共享全局可变字段。
  可复用库或独立运行实例确需选择不同日志实现时，沿用显式注入；不为传日志逐层增加创建函数。

### 流程：组合表达关系，完整行为逐层展开

- **入口与各级子流程都以流程表达为默认取向**。组织多个行为时，优先用函数组合呈现顺序、
  并发、业务分支与重复，例如 `pipeline`、`parallel`、`branch`、`loop`，名称沿用项目能力。
  每次进入子流程，继续展开这些关系，直到局部算法或具体操作；函数所在层级不改变这一取向。
  重要参数关系用简短匿名函数就地说明，不增加无语义转发。
- 影响路径或结果的策略在对应阶段就地展开。单项可用 `withFallback(...)`，多项优先用平直的 Fluent 链，
  一起呈现作用域与顺序；不多层套包装，也不单为缩短入口提取策略别名。
- 按完整业务行为命名子流程，命名不自动要求独立文件。字段计算、游标推进、集合扫描等局部算法，
  以及事务、资源释放和异常处理的具体边界直接实现；其中若包含多个业务阶段，仍按阶段组织。
  已有简单显式调用可保留，条件是顺序与数据关系已就地可读，改成组合只会增加包装或参数搬运。
- 多个阶段需要复用中间结果时，优先使用**本次执行的可变 Context**。串行阶段原地写入自己负责的字段，
  再返回同一 Context，避免反复包装返回值或展开复制；每次执行创建自己的实例，明确字段的读写与可用时机。
  无需累积状态的简单数据流仍可直接传值，不把所有业务都改成一个全局上下文。
- 并发分支只读取所需输入并返回独立结果，**全部成功后在汇合处集中写入 Context**。
  不让分支完成时各自写入共享字段，也不假设并发原语会自动合并状态、取消任务或回滚副作用。
- 业务阶段拥有日志事实的含义；记录中间结果并继续传值时可用 `tap`，
  完整操作的耗时、状态与失败交给边界观测或已有追踪能力。业务 Context 与日志上下文分别承担职责，
  诊断输出的失败策略和必须持久化的业务记录各按实际契约设计。组合与注入本身不保证纯函数或日志失败隔离。
- **当前阅读单元最多两层组合/控制嵌套，不出现第三层**。如 `pipeline` 为第一层，其中的 `parallel / branch`
  为第二层；平直策略链、参数配置与函数定义不额外算控制层，匿名函数里的控制嵌套仍需计入。
  用卫语句、提前退出和完整子行为整理多层 `if / for`，第三层按业务语义下沉，
  不靠碎片函数隐藏复杂度；这个边界不限制目录或完整调用链的业务层级。
- 阶段关系为主时用 Flow，节点转移与回环为主时用 Graph 或已有状态机，两者可分层配合。
- 表达方式与支撑能力一起设计。优先复用已有能力；缺少支撑时，在已授权范围内主动补齐所需的组合或策略能力。
  流程与阶段拥有业务判断，组合与策略工具负责阶段衔接和策略执行；工具通过明确契约承接行为，不内置具体业务规则。

### 留白：按共同意图组织阅读

同一意图的步骤相邻，意图转换处留空行，例如取得数据与处理数据、业务执行与异常处理。
分组由当前行为决定，不规定每个阶段都空一行。相关策略就近逐行展开，复杂参数按关系换行，
Graph 节点间留白以区分行为与转移。先通过排版显露语义，再按独立阅读与修改价值提取完整子流程。
注释解释意图、取舍与关键约束，步骤由名称和组合说明；遵循项目格式约定，保留清楚的视觉层次。

## 4. 应用与验证

### TODO 跟踪

多步骤任务开始前建立 TODO，按实际工作列出调查、设计、实施、清理与验证等具体任务，
执行中及时更新待办、进行中与已完成状态。有任务工具时使用工具，否则维护 Markdown 勾选清单。
完成一项更新一项；验证未执行或存在阻塞时明确标出，不以“代码已写完”代替“验证已通过”。
简单单步任务可省略，不为填满清单扩大范围。

### 执行流程

按任务规模执行，不重复启动完整架构讨论：

1. **查明阻力。** 从用户要完成的事情出发，读项目约定、相关目录与代表性调用链，核对现有设计的有效部分，
   区分归属、维度、密度、粒度和执行表达问题；
   无代码时标明样本是假设，不因“太碎”直接合并，也不因“要扩展”直接搭框架。
2. **展示完整阅读路径。** 给出必要的目录与流程，沿一条代表性链路逐层检查到局部算法或具体操作。
   每层核对阶段、数据、策略和副作用；对有多个业务阶段的子流程展开组合，不能在命名后停止检查。
   向用户展示足以判断设计的关键片段，无需贴出整条链路的全部代码。
3. **推演高概率变化。** 新增成员、修改局部规则或共同规则应有自然位置；
   说明新增抽象的阅读收益与代价，不推演所有未来可能；频繁参数搬运、多处同步配置或无信息增益的跳转提示边界需要调整。
4. **按授权落地。** 纯定位问题可只整理目录；职责分散才需要同步收拢职责。
   明确调用方、契约、测试和文档范围，将改进融入现有合理结构，
   同步清理被替代的内部路径、配置、依赖与说明，保留或迁移必要公开入口。
   重大归属取舍结合 `architecture-co-design`，复用已有共识；讨论不等于实施授权。

结构调整保留输入输出、权限与业务校验、数据依赖、副作用顺序、事务与资源所有权，
以及异常、超时、取消、重试、补偿、并发、幂等和生命周期语义。
顺序改并行、新增回退等是行为变化，需明确授权并验证；共同契约不能抹平成员真实差异。
权限、事务、协议适配等真实边界不能因代码短或只有一个实现而删除。

验证服务于真实行为、稳定契约和重要失败风险，已有证据足够时复用。
只为缺乏保障的重要行为补充必要测试；简化实现时同步移除重复、失效或仅追随私有实现的测试与夹具。
文案和纯说明修改不新增单元测试，必要的业务、权限与数据完整性验证按真实风险保留。

交付结构判断、必要样本、收益与代价、实际修改范围及待验证项。
区分阅读/变化推演与编译、测试、运行结果，不把文档检查当作行为验证。
