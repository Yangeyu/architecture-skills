# Graph Expression

节点、转移、回环或动态依赖本身是主要阅读信息时，采用 Graph 或已有状态机。
阶段关系为主时用组合，二者可分层配合；一个 if、循环或较深嵌套不构成升级理由。
以下 DSL 只说明表达，使用现有工具时以其真实契约为准。

## 1. 节点行为、转移与子图一起阅读

```ts
graph("analysis", {
  prepare: step(prepare)
    .next("research"),

  // 研究内部流程在子图展开，父图保留阶段间的转移。
  research: subgraph(researchFlow)
    .next("analyze"),

  analyze: step(analyze)
    .next("verify")
    .when(qualityInsufficient, "research"),

  verify: step(verify)
    .next("publish")
    .when(verificationFailed, "repair"),

  repair: step(repair)
    .next("verify"),

  publish: step(publish),
})
```

每个节点就近表达执行什么、正常去哪、什么条件下偏离。
节点间留空行，行为与转移分行，先扫描默认路径，再阅读条件偏离。
这种局部组织是重点，Fluent 只是实现方式之一。

本例中 `.next()` 表示没有条件命中时的默认去向，`.when()` 表示节点完成后的业务条件路由，
不是先执行 next 再判断 when，也不自动捕获执行异常。
没有自然默认路径时如实列出分支，不为外观制造主链。

## 2. 用完整子图展开复杂度

`researchFlow` 承担一个完整研究子流程，可在内部继续使用 Graph、组合或普通函数。
子图应有明确的职责、输入输出、完成与失败方式，以及对外可见的状态和副作用。
父层的 `analyze → research` 等转移仍需保留，不能为了分层删去真实关系。

转移多但属于同一清楚的领域决策时可以一起表达；混合多个业务层次时，再提取决策或子图。
提取后仍应追踪决策依据与可能目标，而不是藏进不透明的 `route()`。
按语义与阅读范围分层，不按节点数量切块；频繁跨子图跳转可能说明边界有误。

## 3. 明确转移契约

在已有 API 或新表达中确认：

- 起点、完成、等待和结束如何表示；
- 条件读取执行前还是执行后的状态，多个条件同时满足时如何选择；
- 没有条件命中、无默认路径时的行为，声明顺序是否有执行含义；
- 异常、超时、取消、重试与业务路由如何区分；
- 回环如何更新状态、终止或被取消；
- 若支持并发，依赖就绪、汇合、失败与资源清理如何处理。

这些语义由工具契约决定，不能从 `.next()` 等名称推断，也不能用同一名称混淆默认去向、重试和异常处理。
关键约束可由类型、接口或邻近注释表达，无需展开执行引擎实现。

## 4. 阅读结构与运行表示分开

业务表达优先让节点与相关转移局部可读，不让开发者跨分散的节点表、边表重建行为。
底层仍可使用独立 nodes / edges；已有框架如此组织，也不因此要求改写框架。
全局拓扑可由同一事实来源生成辅助视图，避免维护两套易漂移的定义。

不把运行时便利转嫁为业务阅读成本，也不为 Graph 语法预建 IR、调度或恢复设施。
结构调整后验证真实转移与数据依赖，特别检查条件重叠、失败和回环终止；
阅读推演不能代替实际运行验证。
