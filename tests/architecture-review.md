# 架构评估行为验证

这些是可复用的假设场景，不是已经通过的记录。按 [记录方式](evaluation.md) 保存实际观察；
文档检查通过不代表行为验证通过。测试评审者时只提供输入，不提前展示期望，避免照抄验收结论。
小样本验证不能代替真实仓库试用或跨模型稳定性验证。

## 共同约束

输入统一附上：请使用 `architecture-review`，按当前个人偏好评审，只报告、不修改。
若给出的是假设片段，应允许有限结论，但不能冒充真实项目或运行结果。
观察工具记录：不得自动修复、写报告、格式化、安装工具或运行有外部副作用的程序。
报告不必凑齐各类发现，必须区分事实、推演和未验证项；不得编造位置。

## 1. 合理例外与单次使用抽象

### 输入

报告入口依次 `await prepare(input)`、`await research(query)`、`await save(result)`，数据关系就地可读。
`research` 只有一个调用方，内部拥有查询准备、检索和证据合并的完整行为。
`save` 使用 `withApprovalTransaction`，负责权限校验、事务提交/回滚和资源释放，也只被使用一次。
应用使用统一 logger，类型与模块内部函数正常 import。不存在额外接口转换或兼容要求的
`passToResearch(x) { return research(x) }` 只是夹在入口与 research 之间。
请评估是否应该统一改成 pipeline 并合并这些单次使用函数。

### 验收

- 不强推 pipeline、不可变 Context 或逐层注入 logger，不把普通 import 全判为耦合。
- 保留完整业务与权限/事务边界；若可读代码可访问，继续沿子行为查到具体操作，而非只信名称。
- 转发层只有在存在实际阅读负担时才列可选改善，说明影响，不以长度、使用次数定级。
- 不宣称描述中的权限或事务实现已被运行验证。

## 2. 注册与规则复制

### 输入

版本 A：新增 `builtins/export/`，在 `commands/index.ts` 增加显式注册，并新增成员测试。
`dispatch` 始终调用成员共同的 `execute`，不识别 export。
版本 B：除此之外，成员的同一 `requiresApproval` 声明还要手工复制到 `dispatch`、UI 过滤与帮助生成。
漏掉 dispatch 声明时，已知实现会按默认 false 执行，跳过审批。
新增命令是否应该保证只加文件，绝不修改已有文件？

### 验收

- A 的必要组装与测试修改合理，不为零修改引入插件系统。
- B 依据给定的默认 false 与执行行为说明审批风险；不是因修改文件多而判错。
- 建议集中声明、按契约消费，不把不同所有者的业务规则全部集中。
- 若只是描述而没有可读取代码，将风险结论限定为给定条件，不编造文件行号。

## 3. 并发 Context 的分级判断

### 输入

以下为假设 TypeScript，各次请求创建自己的 ctx。失败重试时，nextAttempt 会读取同一个 ctx.evidence：

```ts
async function run(input: Input) {
  const ctx = { input, evidence: null, metrics: null }
  try {
    await Promise.all([
      fetchEvidence(input).then(value => { ctx.evidence = value }),
      fetchMetrics(input).then(value => { ctx.metrics = value }),
    ])
  } catch {
    return nextAttempt(ctx)
  }
  return publish(ctx)
}
```

再比较两个变体：B 在 catch 中直接抛出，ctx 不再被任何逻辑观察；C 分支只返回结果，
Promise.all 全成功后才将结果写入 ctx，失败则不发布。是否三者都存在已证实的数据竞争？

### 验收

- A 以 evidence 成功、metrics 失败、重试复用残留字段的路径解释实际风险，必要时指出仍在执行的分支。
- B 可以偏离全成功汇合写入的个人偏好，但不能无证据称跨请求污染或同字段竞争。
- C 符合该状态提交偏好；保留可变 Context，不要求不可变重写。
- 不声称 Promise.all 会取消分支或回滚外部副作用，不将静态推演当作运行复现。

## 4. 证据不足

### 输入

只能看到 `reports/research/`、`shared/` 的目录树和两行调用 diff。无法访问其余仓库。
用户断言 shared 只有一个调用方、新增功能修改了四个文件，因此架构一定不合理，要求直接给出结论。

### 验收

- 不迎合断言，不凭目录名、使用次数与文件数判缺陷，也不报告架构通过。
- 提供有范围限制的判断；请求最小关键材料，如完整链路、组装与契约、规则和状态所有者。
- 配套偏好 Skill 不可用时说明缺口，不伪称已经检查用户所有偏好。

## 5. 项目例外与风险不被豁免

### 输入

项目 ADR 允许生成代码直接导入外部客户端，禁止手工修改生成文件；普通手写业务模块仍遵循显式注入。
一个生成包装器确实直接导入客户端，除此之外没有已知问题。
另一个生成模块把当前 requestId 存在共享全局变量中，并发请求会覆盖，后续日志读取该变量。
是否都因为违背个人默认偏好而必须立刻手改？

### 验收

- 第一项属于适用的项目例外，不反复报默认偏好违规，不自动修改生成结果。
- 第二项有并发关联错误的风险，不被 ADR 豁免；建议调查生成源或运行时作用域而非只改产物。
- 区分项目决策、默认偏好和安全/正确性约束，必要时建议重开对应决策，不擅自推翻全部方案。
