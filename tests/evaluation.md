# Skill 行为验证场景

这些场景用于修改 Skill 后的人工或独立会话验证，不是已经通过的测试记录。

在具备相应 Skill 的新会话中提供场景，观察实际回答与工具行为。无需每次全部运行；按变更影响选择场景。示例业务均为假设，不是现有项目事实。

| 场景 | 示例输入 | 期望行为 | 需要警惕 |
| --- | --- | --- | --- |
| 简单流程 | 现有函数依次准备数据、分析、保存，数据依赖明确，是否必须换成 pipeline？ | 已有顺序与数据关系就地可读，且组合只增加包装或参数搬运时保留；新增或调整多阶段组织时优先组合 | 机械创建 PipelineRuntime 或统一大 Context |
| 阶段与并发清晰 | 准备数据后，两路独立研究并发执行，再合并证据、分析、保存；阶段接口清楚，但项目没有组合工具。如何让整体流程更直观？ | 优先组合顺序与并发关系，完整子行为按语义命名；缺少工具时补齐最小支撑，说明输入、汇合和失败契约 | 因缺少现成工具一律退回 await，或强制采用一套 pipeline/parallel DSL |
| 多处数据依赖 | 发布报告同时需要初始请求、研究证据和验证结果，跨阶段结果如何承载？ | 优先本次执行的可变 Context，串行阶段原地写入自己负责的结果并返回同一对象；关键参数关系可用匿名函数显式衔接 | 把 Context 一概视为反模式，强制逐阶段包装或展开复制；或使用全局对象、全部可选字段与非空断言掩盖读取顺序 |
| 并发 Context 汇合 | 两路检索读取同一查询，结果写回流程 Context；一条失败时怎样处理？ | 分支返回独立结果，全部成功后由汇合处集中写入；失败不执行本组字段写入，不承诺回滚既有状态和外部副作用 | 各分支完成就写共享字段、结果元组冒充 Context，或声称 Promise.all 会自动取消任务及回滚 |
| Context 执行契约 | 两份报告同时运行，阶段会修改并返回 Context，如何避免串扰？ | 每次执行创建自身 Context，明确字段的可用时机和写入者；重试/回退确认残留状态与重置需求 | 多次运行复用同一个可变实例，返回 void 却假定 pipeline 自动传回 Context，或重试时读取上一尝试的半成品 |
| 阶段策略可见 | 研究发生特定可恢复错误时可使用缓存，应该隐藏在 research 内部，还是在组合处表达 withFallback？ | 优先组合处显式表达，阶段本体保持简洁；说明策略输入输出、适用错误与取消、回退失败等契约 | 为入口短而隐藏业务策略；按名称猜测所有异常都应被吞掉，或把展示样例变成新增回退行为 |
| 流程与策略分工 | 主流程包含并发检索，网络任务需要超时、重试与缓存回退，如何组织？交换 timeout 和 retry 的调用顺序会怎样？ | 入口与子流程均优先组合阶段，多策略就地 Fluent 展开；依据实现说明策略作用域与顺序，缺少实现证据时标明假设 | 从链式外观猜测执行语义，或为缩短入口隐藏策略 |
| 业务分支与局部计算 | 证据不足时补充检索；另有标题 trim 后取默认值，两个判断怎样表达？ | 前者优先 branch 展示业务路径，后者在所属函数内直接计算 | 把业务路径藏进匿名 if，或强制每个字段判断使用 DSL |
| 两层完整样例 | pipeline 内并列 parallel 和 branch，parallel 的一个任务带平直的 timeout/retry/fallback 策略链，是否必须拆分？ | 接受整体就地可读的两层结构；策略链、参数对象和函数定义不当作额外控制层 | 机械计算括号或缩进，把已清楚的策略移走；或在匿名函数中偷偷加入第三层控制 |
| 外部能力注入 | 复制命令需要对话读取与剪贴板写入，目前都只有一个实现，应该直接导入还是创建时注入？ | 优先 createCopyCommand({ readConversation, writeClipboard })，组装选择实现，成员保留完整行为 | 仅因无替换需求而否定注入；或扩大为依赖容器、大依赖对象、层层 Factory 转发 |
| 深层组合 | pipeline 内的 parallel 又包含 pipeline，Agent 推理与工具判断也堆在同一阅读单元，如何整理？ | 第三层组合/控制按完整业务行为下沉；每个阅读单元保留最多两层，局部判断可用卫语句 | 生成无语义 innerFlow1/2，匿名函数隐藏同一控制树，或直接强制 Graph 化 |
| 内部流程表达 | 报告顶层已清楚，但 research 内部混杂查询准备、并发检索、合并，某个检索源又包含构造、分页、解析和去重。只把它们藏在函数名后面是否足够？ | 沿 report → research → 检索源 → 分页检查到底：各层业务阶段优先组合，游标推进与退出用局部循环；展示关键片段，保持真实数据契约 | 只优化顶层或检查一层子流程就停止；以局部实现为由隐藏业务阶段，或强制每个具体操作使用 DSL |
| 业务层级与局部控制深度 | report 调用 research，research 再调用具体检索流程，各层都可直接读懂；是否因为调用层数增加就必须扁平化？ | 保留有信息收益的业务层级；两层边界针对当前阅读单元，不限制目录和完整调用链深度 | 将业务层级限制成两层，或反过来以调用链不设上限为由允许局部第三层控制嵌套 |
| Graph 表达 | 审查一个含验证、修复回环与发布节点的 Graph | 加载 Graph 参考，检查局部转移、默认路径、条件优先级和终止语义 | 只改 DSL 外观，隐式改变异常或转移语义 |
| 两个 Skill 协作 | 按已经确认的模块职责整理顶层调用，不改变接口，直接实施 | 复用已确认信息，在授权内推进，必要时加载结构参考 | 重新启动架构问卷，重复做两套推演 |
| 边界尚不明确 | 改一个报表规则需要跨多个技术目录，先讨论方案 | 共创定位真实阻力，给最小样本，不未经授权修改代码 | 直接搬文件、套目录模板，或把建议称为共识 |
| 组合支撑与业务归属 | 已确认采用阶段组合和就地策略表达，并授权实现，但项目没有对应工具。请实现证据不足时补充检索、网络请求失败时按策略重试的流程。 | 补齐组合与策略能力，验证类型、数据和失败契约；证据判断与可重试错误由业务传入，工具负责分支选择和重试执行 | 只交付调用样例，在工具中硬编码报告规则，或扩张成通用执行引擎 |
| 并发语义 | 为了代码简洁，把依次读取和写入改为 parallel 可以吗？ | 先检查依赖、副作用和错误/取消语义，不默认等价 | 把并行重排当作纯结构重构 |
| 小规模命令集合 | commands 目前只有两个内置命令，但预计持续增加，是否与 dispatch、catalog 放在根目录？ | 从一开始用 builtins 区分稳定组织机制与可增长成员集合，允许必要组装变化 | 仅因文件少就混排；或为集合目录创建插件运行时 |
| 小规模研究组成 | research 中只有入口、查询准备、两种检索与证据合并，是否立刻建立 sources？ | 可直接平铺实际组成，短小局部步骤可留同文件；进一步分组由信息密度与语义收益决定 | 发现可命名集合就机械增加目录，或设置固定文件数量阈值 |
| 成员与步骤粒度 | copy 是很短但完整的命令，export 有丰富内部组成，prepareQueries 是仅此处使用的短步骤；research 只被调用一次，但包含完整的检索与合并流程。如何组织？ | 接受 builtins/copy.ts 与 builtins/export/ 并列，prepareQueries 可留同文件；依据阅读收益、修改影响和维护成本判断 research 的边界，单次使用不妨碍封装完整子流程 | 为对称给所有成员建目录，每个能命名的步骤都拆文件，或仅因无复用而拒绝有价值的抽象 |
| 纯定位整理 | 职责与依赖本已清楚，只需将混排成员移入对应集合目录，是否必须同时改职责？ | 目录分组本身可以完成定位改善，按实际影响同步导入和必要验证 | 为满足清单扩大成架构重构；反过来仅搬文件掩盖真实职责问题 |
| 视觉组织 | 流程逐步留白，Graph 节点及 next/when 又压成连续单行，怎样整理？ | 按共同意图分组，相关步骤相邻，节点间空行与分行转移帮助扫描；注释解释意图和约束 | 机械逐行留白或压缩视觉层次，为排版拆碎函数，为每行添加复述性注释 |
| 平坦控制流 | 一个函数用多层 for/if 组织报告筛选与发布，如何改善？ | 用卫语句、continue 和完整的命名子行为保持主路径平直，保留判断顺序、顺序等待与失败/清理行为 | 只把嵌套搬入新名字，随意改变 return/break/continue 作用域，或展平时改为并发 |
| 日志架构与接入 | 应用已有统一 logger，给报告流程增加数量、耗时与失败记录，需要每层注入 logger 吗？ | 复用应用统一入口，业务产生事实，操作边界负责执行观测；关联字段由作用域提供，库或独立实例的不同实现需求可注入 | 把所有依赖都强制参数化，为每次日志上下文重建业务流程，或反过来禁止合理的库级注入 |
| 日志作用域与重试 | 两份报告并发运行，各有 runId，两路来源要标签，网络重试后成功或回退缓存。 | 运行入口建立上下文，日志调用时读取；分支独立扩展，区分尝试和最终结果、耗时范围，跨消息边界显式传播关联 | 修改共享 logger 的当前请求字段，组装时捕获请求上下文，层层重复错误堆栈 |
| tap 与记录可靠性 | 研究结果后记录数量并继续分析；日志后端可能失败，审批审计必须和审批一起保存，规则解释需返回给用户。 | tap 等待回调并保留原值；诊断失败策略由适配层承担；审计按业务事务或交付契约设计，计算说明可随结果累积 | 假定 tap 自动吞错或负责完整耗时，把日志排队或 Writer 当持久化保证 |
| 现有设计融合 | 现有目录、组合、Context 与验收机制有效，希望整体优化并增加日志能力。 | 核对原有职责与契约，把新能力融入对应位置；只替换有证据的不合理部分，保留有效规则与验证 | 将整体优化理解为删除重建，或只追加新规则而保留互相矛盾的旧说明 |
| TODO 与验收 | 多步骤修改中用户询问进度；格式检查已通过，执行行为尚未验证。 | TODO 跟踪进度，交付验收核对结果；保留两者并按任务使用，区分修改、推演、测试与未验证边界 | 将 TODO 与验收混为一谈后删除其一，或把文档检查当作行为验收 |
| 克制测试与清理 | 合并重复实现，旧测试仅验证转发与私有赋值，但仍有权限和事务测试。 | 同步清理无用调用、配置、测试与夹具，复用充分验证，保留稳定契约和重要风险保障 | 为删除代码新增旧文件不存在断言，按分支机械补齐测试，或删除必要业务验证 |

## 架构评估专项

默认只读、证据分类、合理例外与防误报，使用 [架构评估行为验证](architecture-review.md)。这些场景验证评估方法，不另定义一套设计偏好。

## 记录方式

每次验证记录以下必要信息即可，可放在对应 commit 或 PR 描述中：

- 仓库 commit、客户端及模型；
- 场景输入与实际加载的 Skill / references；
- 观察到的行为及结论：符合 / 不符合 / 未验证；
- 不符合时的具体证据和下一步调整。

不要以文件检查通过代替行为验证，也不要把一个会话中的成功推广为所有模型都能稳定遵循。
